# Повторы и надёжность

SDK сам повторяет запрос, только когда это безопасно. Главное правило: запрос, который сервер мог уже
выполнить, не повторяется — дубль письма хуже ошибки.

## Когда SDK повторяет запрос

| Ситуация | GET / PUT / DELETE | POST (отправка письма) |
|---|---|---|
| Соединение не установлено (DNS, refused, open timeout) | повтор | повтор — запрос не ушёл |
| Таймаут чтения, обрыв после отправки | повтор | **нет** — письмо могло уйти |
| 429, 503 (сервис отказал до обработки) | повтор | повтор |
| 500 / 502 / 504 | повтор | **нет** — письмо могло уйти |
| `ErrorCode 36` (временная ошибка отправки) | повтор | повтор |
| `ErrorCode 100` (внутренняя ошибка, «повторите позже») | повтор | **нет** |
| Ошибка TLS / сертификата | **нет** | **нет** |

Особые случаи:

- безопасные POST — проверка шаблона (`templates.validate`), архивация и возврат канала из архива,
  добавление и удаление адресов стоп-листа — повторяются как GET;
- `inbound_messages.bypass`, `inbound_messages.retry` и `templates.push` повторяются только как
  отправка письма — когда запрос точно не был выполнен (соединение не установилось, 429/503,
  `ErrorCode 36`), но не после 500/502/504 и не после обрыва уже отправленного запроса;
- DELETE повторяется, поэтому если первый ответ потерялся, повтор может вернуть «не найдено» для уже
  удалённого объекта.

## Задержка между попытками

По умолчанию — 2 повтора (то есть до 3 попыток). Задержка растёт экспоненциально: до 0,5 → 1 → 2 с …
со случайным разбросом, но не больше 8 с. Если сервер прислал `Retry-After` (секунды или дата), SDK ждёт
указанное время, но не больше 30 с.

```ruby
require "haskimail"

# Глобально
Haskimail.configure { |config| config.max_retries = 3 } # от 0 до 10

# Для одного клиента: без повторов, например в веб-запросе с жёстким таймаутом
client = Haskimail::ServerClient.new(ENV.fetch("HASKIMAIL_SERVER_TOKEN"), max_retries: 0, read_timeout: 10)
```

С `logger` каждый повтор пишется в `warn`: `Haskimail retry 1/2 in 0.37s (HTTP 503)`.

## Что делать, когда повторы исчерпаны

После последней попытки бросается исключение (см. [[Обработка ошибок]]). Для отправки письма решите по типу
ошибки:

```ruby
def deliver_order_email(client, order_id)
  client.emails.deliver(from: "shop@example.com", to: "ivan@example.com", subject: "Заказ №#{order_id}",
                        text_body: "Заказ оформлен", metadata: { "order_id" => order_id.to_s })
rescue Haskimail::ConnectionError => e
  raise unless e.request_sent? # запрос точно не ушёл — можно повторить позже целиком

  # Письмо могло уйти: найдите его в журнале сообщений, прежде чем отправлять снова
  warn "Заказ #{order_id}: результат отправки неизвестен"
rescue Haskimail::ServerError, Haskimail::UnexpectedResponseError
  warn "Заказ #{order_id}: письмо могло уйти, проверьте журнал сообщений"
end

deliver_order_email(Haskimail::ServerClient.new, 1042)
```

Журнал отправленных писем — в [[Исходящие сообщения]]; например, по тегу или получателю за последние
минуты.

## Потокобезопасность

Клиенты и их настройки неизменяемы после создания, транспорт открывает новое соединение на каждый запрос.
Один экземпляр `ServerClient` или `AccountClient` можно держать в константе или инициализаторе и
использовать из многих потоков.
